# 算法说明

## 1. 问题定义

给定用户起点 `p=(lat,lon)` 与时间预算 `T∈{30,45,60,90}` 分钟,求城市区域内所有满足
"从 `p` 出发,经步行接入 + 公交/地铁网络行驶,估计耗时 ≤ T" 的空间位置集合,
即公共交通 **理论可达区域**(等时圈)。

系统输出的是**估计时间/理论可达时间**,不是实时导航结果。

## 2. 网络模型

- **节点**:公交/地铁站点,属性 `(id, name, lat, lon, type∈{bus,metro}, city)`
- **边**:相邻站点间的连接 `(from, to, distance_m, mode∈{bus,metro,walk})`,按无向边处理
- 平行边(多条线路共用同一站对)保留估计时间最短的一条

## 3. 时间权重模型

所有参数可配置(`backend/config/config.json`),默认值:

| 参数                  | 默认值 | 说明                                           |
| --------------------- | ------ | ---------------------------------------------- |
| `walkingSpeedKmh`     | 5      | 步行速度                                       |
| `busSpeedKmh`         | 20     | 公交平均运行速度                               |
| `metroSpeedKmh`       | 35     | 地铁平均运行速度                               |
| `transferPenaltyMin`  | 5      | 换乘/上车固定附加时间                          |
| `maxWalkingDistanceM` | 1500   | 附近站点查询接口的默认半径(接入计算不再设上限) |
| `walkLinkMaxM`        | 200    | 站点步行接驳边距离上限(同站异ID/换乘),0=关闭   |
| `entryStationsLimit`  | 6      | 最多取几个附近站作为多源起点                   |

边权折算(分钟):

```
bus   边: t = d / (v_bus   × 1000/60)
metro 边: t = d / (v_metro × 1000/60)
walk  边: t = d / (v_walk  × 1000/60) + transfer_penalty
```

walk 边计入换乘惩罚:经过它意味着一次模式切换/上车,等待时间在该惩罚中简化建模。

### 3.1 站点步行接驳边(碎片化修复)

CPTOND 中同一物理站点可能存在多个 ID(如 "客村"/"珠影(地铁客村站)" 相距 8m、
"小北(停东行)"/"小北1" 相距 0m),且数据不含任何跨模式连接——直接建图会产生
30 个连通分量(公交网与地铁网完全断开),换乘不可达、部分城区(如财厅一带)整片
不可达。

修复:建图时为直线距离 ≤ `walkLinkMaxM`(默认 200m,可配置)的站点对自动补充
双向 walk 接驳边(空间哈希近邻查找)。换乘惩罚保证接驳边永远不比乘车快,
只在换乘/同站接驳时被使用,不会产生"沿街步行跳站"捷径。

效果(广州实测):连通分量 30 → 12(主分量覆盖 99.7% 站点),
剩余碎片为数据中本就无线路连接的码头渡口站;
诊断工具:`go run ./cmd/netcheck -config config/config.json`。

## 4. 多源 Dijkstra

用户起点一般不在站点上,取**距离最近的** `entryStationsLimit`(默认 6)个站点作为 Dijkstra 起点,
不设步行距离上限(远站步行成本高,会被 Dijkstra 竞争自然淘汰),初始距离 = 直线步行时间 + 换乘惩罚:

```
sources = { stop_i: haversine(p, stop_i)/v_walk + penalty  |  i ∈ 最近的 entryStationsLimit 个站点 }
```

实现(`internal/graph/dijkstra.go`):

- 二叉最小堆(`container/heap`)优先队列,懒删除(出堆时与 `dist[]` 比对,过期跳过)
- 剪枝:`dist + edge > maxTime` 的节点不入堆,提前终止
- 复杂度 `O((|V|+|E|) log|V|)`,单城市全图毫秒级完成

## 5. 空间网格法

不能把可达站点直接连成多边形(外围可达 ≠ 中间可达),采用网格近似:

1. 对可达站点集合求包围盒,向外扩 `walkRadius + cellSize`
2. 划分 `500m × 500m` 网格
3. 每个网格中心 `c`,在步行半径 `walkRadiusM`(默认 800m)内找站点:
   `time(c) = min_i( dijkstra_time(stop_i) + haversine(c, stop_i)/v_walk )`
4. `time(c) ≤ T` 的网格即为可达区域成员(网格计算上限为最后一个分级阈值,
   即 90 分钟:超过部分不遍历、不生成、不返回)
5. 分级:`[0,30] → 等级1, (30,45] → 2, (45,60] → 3, (60,90] → 4`(共四级,对应前端四色图例)

**网格可达性完全由公共交通网络计算出的可达时间决定**(Dijkstra 结果 +
末段步行接入),不使用凸包/外包络/空间插值。河流、山体等地理阻隔因此被
正确处理:两岸有桥上线路连接时,对岸按真实网络时间正常可达;若某区域
没有(经网络可达的)站点,即使直线距离很近也不会被判为可达——但需注意,
末段 ≤800m 的步行接入仍使用直线距离近似(见第 7 节误差来源),
水域宽度大于步行接入半径时不会跨河泄漏(有跨河最小测试用例覆盖:
`TestIsochroneAcrossRiver` / `TestIsochroneNoBridge`)。

空间检索使用均匀网格哈希索引(按 `maxWalkingDistanceM` 划格,查询 3×3 邻域),
万级站点规模下无需 R-tree。

## 6. GeoJSON 输出

每个可达网格输出一个 Polygon Feature:

```json
{ "type": "Feature",
  "properties": { "time_min": 37.2, "level": 2 },
  "geometry": { "type": "Polygon", "coordinates": [[[lon,lat]×5]] } }
```

前端 Leaflet 按等级着色渲染。

## 7. 误差来源(论文可直接引用)

- 平均速度模型 vs 真实时刻表/拥堵
- 直线步行距离 vs 实际步行路径(约高估 1.2~1.4 倍系数可校准)
- 换乘固定惩罚 vs 真实等待时间
- CPTOND 站间几何长度 vs 实际运营里程
